## 1. Project Overview

**Service Tech** is a repair/service-job tracking system for two
Thailand-based retail brands (Bruno Thailand, Join Lux Club). The main
application (`src/`, React 19 + TypeScript + Vite) is a staff/customer-facing
web app — see [PROJECT_STATE.md](PROJECT_STATE.md) for its full state. It is
**not** covered further in this document except where it touches the
subsystem below.

This document is scoped to one subsystem: **attachment file storage,
retention, and deletion** — the Cloudflare Worker + R2 + Firestore stack that
handles Service Job photo/document attachments. Earlier versions of
`PROJECT_STATE.md` did not mention that subsystem; current later-sprint
sections record the related public-tracking boundary and source-only status.
The authoritative Worker sources remain `worker/README.md` and
`worker/PRODUCTION_FIRESTORE_ACCESS.md`, both consolidated here.

**F5d-31 source-only hardening:** the default Worker configuration has no
Cron trigger, so an ordinary code deploy cannot activate scheduled work.
`scheduled()` remains present but is not reachable from `fetch()`;
`deletionExecutor` remains unwired. The app's production backend setting now
fails closed unless it is exactly Firestore. Durable Service Job numbering is
transactional in source, but current browser Rules intentionally deny
`numberSequences`; do not deploy that path until a separately approved
Rules/privileged-allocation design exists.

**Why this subsystem exists:** Service Jobs need photo/document attachments
(before/after photos, receipts, reports). Storing file bytes requires an
object store; Cloudflare R2 was chosen. A Cloudflare Worker is the _only_
thing in this entire project allowed to talk to R2 — no R2 access key or
secret exists anywhere else, including the main app. The Worker also owns a
narrow slice of Firestore access (attachment metadata: retention timestamps,
deletion state) via its own REST-based client, separate from the main app's
Firebase Web SDK usage, because the Workers runtime cannot use the Firebase
Web SDK.

**Relationship to the main app:** The main app never talks to R2 or to this
Firestore access path directly. It calls the Worker over `fetch()` for
upload/download/delete of attachment bytes
(`src/repositories/workerAttachmentsRepository.ts`), and reads/writes
attachment _metadata_ itself via the Firebase Web SDK
(`src/repositories/firestoreAttachmentsRepository.ts`) against the same
`serviceJobAttachments` Firestore collection the Worker reads. Two different
clients, one collection, by design (DECISIONS.md #022).

```
                                  │  collection:          │  │  (0 objects,      │
                                  │  serviceJobAttachments │  │  no public access)│
                                  └────────────────────┘  └──────────────────┘
```

**Attachment lifecycle / retention flow:**

```
upload (via Worker fetch())
   │
   ├─► R2: object bytes stored at
   │      service-jobs/{jobId}/{category}/{uuid}-{name}
   │
   └─► Firestore (serviceJobAttachments/{docId}):
          docId = R2 key with "/" → "__"
          path = real R2 key
          deleteAfter = null, retentionStatus = 'active'   (job still open)
          deletedAt = null
                │
                │  ServiceJob.closedAt gets set (job closes)
                ▼
       reconciliation (manual today, backfillAttachmentRetention() /
       retentionSweep.ts) computes:
          deleteAfter = closedAt + 365 days
          retentionStatus = 'expiring-soon' once within 30 days of
                             deleteAfter (or already past it), else 'active'
                │
                │  now >= deleteAfter  (the ONLY eligibility signal —
                │  retentionStatus is explicitly NOT used for this)
                ▼
       selectDeletionCandidates() → up to 50 eligible candidates/run
                │
                ▼
       runDeletionExecutor()  [UNWIRED — not reachable from any live path]
          for each candidate:
             1. fresh Firestore re-read
             2. re-check eligibility (incl. deletedAt still null)
             3. re-validate R2 key namespace
             4. head() the R2 object
                ├─ found  → delete() it
                └─ null   → already gone (idempotent no-op)
             5. mark Firestore: deletedAt = now
                (document is RETAINED — never hard-deleted)
```

## 5. Current Data Lifecycle

- **Upload:** the main app calls the Worker's `POST /files/...` route with
  file bytes. The Worker writes to R2, returns the generated key. The main
  app then writes a `serviceJobAttachments` Firestore document (via the
  Firebase Web SDK, `firestoreAttachmentsRepository.ts`) with `deleteAfter:
null`, `retentionStatus: 'active'`, `deletedAt: null`.
- **Firestore metadata:** one document per attachment, doc ID = the R2 key
  with `/` replaced by `__` (deterministic, collision-free). Real key is
  stored in the `path` field.
- **R2 object:** the actual file bytes, addressed by the same key.
- **Retention calculation:** `computeAttachmentRetention(closedAt, now)` in
  `src/services/attachmentRetention.ts` (`deriveRetentionStatus()` shared
  with the Worker's copy) — `deleteAfter = closedAt + 365 days`;
  `retentionStatus` becomes `'expiring-soon'` starting exactly 30 days before
  `deleteAfter` (inclusive) through and past it. Attachments on still-open
  jobs (`closedAt === null`) stay `deleteAfter: null`, `retentionStatus:
'active'` forever until the job closes.
- **Deletion candidate:** `selectDeletionCandidates()` in
  `worker/src/deletionSafety.ts` — an attachment becomes a candidate only
  when `now >= deleteAfter` (never based on `retentionStatus` alone — that
  field can read `'expiring-soon'` for up to 30 days before an attachment is
  actually due) **and** `deletedAt === null` **and** its R2 key passes
  namespace validation. Truncated to at most 50 per run.
- **Deletion executor:** `worker/src/deletionExecutor.ts` — see the ASCII
  flow in Section 4. Complete in code, **never invoked by anything live**.
- **`deletedAt`:** `null` = R2 object still exists (or was never eligible for
  deletion). A timestamp = the R2 object was physically deleted and this
  Firestore document is being **permanently retained** as the audit record
  (DECISIONS.md #025) — it is never hard-deleted by the automatic path.

## 6. Safety Architecture

- **Dry-run:** `runRetentionSweepDryRun()` (`worker/src/retentionSweep.ts`)
  shares the real eligibility logic but calls zero write methods — used to
  prove production behavior safely (F5d-11).
- **Fail-closed rules** (`worker/src/deletionSafety.ts`): every ambiguous or
  missing input resolves to "not eligible" / "skip," never to "permit
  deletion." Explicit fail-closed cases: `deleteAfter === null` (open job),
  unparseable `deleteAfter`, `deletedAt !== null` (already processed —
  F5d-17), malformed attachment ID, R2 key outside the attachment namespace,
  missing Firestore metadata.
- **Fresh Firestore re-check:** `recheckEligibilityBeforeDelete()` requires
  an independently-obtained, freshly-read record at delete time — never
  trusts the candidate list built earlier in the run. If `deleteAfter`
  changed since selection (e.g. a staff "Extend Retention" action ran), the
  candidate is refused.
- **R2 namespace validation:** `isDeletionCandidateKeyValid()` reuses the
  same `ATTACHMENT_KEY_PATTERN` the Worker's own upload/download/delete
  routes already enforce (`worker/src/paths.ts`) — a corrupted or
  attacker-influenced `path` value can never be used as a deletion target.
- **Max deletions per run = 50** (DECISIONS.md #024) — a hard, non-optional,
  non-defaulted parameter to `selectDeletionCandidates()`/
  `runDeletionExecutor()`. Callers that omit it get a thrown error, never an
  implicit default.
- **Failure threshold = 3** (DECISIONS.md #024) — `shouldHaltRun()`'s
  circuit breaker; a run halts after 3 genuine destructive-action failures.
  Same non-defaulted parameter contract as the cap above.
- **Idempotency:** `head()` is always called before `delete()`, since R2's
  `delete()` resolves successfully whether or not the key existed. This is
  the only reliable way to distinguish "genuinely deleted this run" from
  "already gone" (e.g. a retried run, or self-healing a prior run's failed
  Firestore write).
- **Audit result:** every candidate produces a `DeletionExecutorResult`
  (`attachmentId`, `objectKey`, `result`, `reason`, `timestamp`, optional
  `errorClassification`) — the full vocabulary is `deleted`,
  `deleted-metadata-write-failed`, `already-deleted`, `skipped`, `failed`,
  `halted`. Verified to never contain secret-shaped content (tested
  explicitly).
- **Firestore metadata retention:** the document is never hard-deleted by
  the automatic path (DECISIONS.md #025) — see Section 5.

## 7. Current Decisions (DECISIONS.md)

Full file at [DECISIONS.md](DECISIONS.md); the ones most relevant to this
subsystem:

- **#022 — Attachment metadata: deterministic doc IDs, durable writes.** R2
  key with `/`→`__` as the Firestore doc ID; `create()`/`deleteById()` are
  genuinely awaited, not optimistic.
- **#023 — Extend Retention: duration reuse, append-only audit array.**
  "Extend Retention" grants another full 365-day period anchored to the
  extension moment; every extension is recorded in
  `Attachment.retentionExtensions`, never overwritten.
- **#024 — Deletion safety limits: max 50/run, halt after 3 failures.**
  Explicit user-supplied policy values, not technical defaults. Does **not**
  change the 365-day retention period, the 30-day expiring-soon window, or
  `deleteAfter` on any attachment — these are execution-throttling limits
  only, and do not by themselves authorize building, wiring, or activating
  a deletion executor.
- **#025 — Firestore attachment lifecycle: retain metadata, mark
  `deletedAt`, never hard-delete.** The approved F5d-16 decision (Option C).
  `RetentionStatus`'s meaning and two-value set (`'active' | 'expiring-soon'`)
  are explicitly unchanged by this — do not conflate the two fields.

  from any live path.
- **The deletion executor is unwired** — not imported by `index.ts`, not
  called from `scheduled()`, no HTTP route. Re-verified by grep every sprint
  since F5d-15.
- **No customer attachment has been deleted** — the only real executor
  deletion was the single uniquely QA-named F5d-18 synthetic object, followed
  by exact metadata cleanup. Automatic deletion remains disabled.
- **No public R2 access** — no public access flag, no custom domain, ever
  configured on `service-tech-attachments-prod`.
- **No unnecessary Cloudflare resources** — exactly 1 Worker, 1 R2 bucket, 2
  secrets exist; nothing else was created "just in case."

## PUB-TRACK-1 — human-enterable secure tracking code (source/offline only)

PUB-TRACK-1 introduces a second, narrow public-tracking credential for manual
customer entry. The code is exactly `SRV-{YYYY}-{MMDD}-{XXXXXX}`. The suffix
is six uppercase base36 characters generated with Web Crypto and unbiased
rejection sampling; no sequential, timestamp-only, customer-derived,
job-ID-derived, or `Math.random` generation is allowed. The space is
`36^6 = 2,176,782,336` (approximately 31 bits), so this credential is not equivalent to the existing
256-bit fragment token. A production rollout remains blocked until a
fail-closed rate-limit/abuse-control policy and trusted issuance transaction
are approved. With no limiter, distributed guessing is unlimited; a basic
per-IP limiter slows casual abuse but is bypassable. Production needs layered
edge/IP/device throttling, monitoring, and fail-closed behavior when the
limiter is unavailable.

`ServiceJob.publicTrackingCodeHash` is the only durable Service Job addition;
it defaults to `null` for new source/mock records, is mapped, and is excluded
from client update patches. The trusted-preparation helper returns
`{ serviceJobId, code, codeHash }` without a route or persistence side-effect.
The private direct lookup is `publicTrackingCodes/{normalizedCode} ->
serviceJobId`; it is bounded and Worker-mediated, never a public Firestore
query or scan.

The app accepts a complete normalized code in `/track#CODE`, strips it from
history, does not use ordinary query credentials, and renders manual labels in
Thai (default), English, Japanese, and Simplified Chinese. The Worker source
adds exact `POST /public/tracking` handling, direct index lookup, one Service
Job read, hash verification, and the unchanged minimal PublicTrackingDTO. It
never reads attachments/R2 or authorizes staff routes. The old fragment-token
route remains for transitional compatibility.

Delivery Note/share helpers may include an already-issued raw code only when
the trusted caller supplies it; they never fabricate a hostname/URL or expose
hashes. No live code was issued. No Rules, Auth, IAM, secret, Firestore,
Worker deployment, R2, production data, or Cron change occurred. Production
remains on Worker version `9a8b83f2-861d-4700-9b4a-05260c4ee661`, Cron is
inactive, and `deletionExecutor` remains unwired.

Validation completed after the implementation: the serialized application
suite passes 112 tests, the local Firestore Rules emulator passes 9 tests, and
the Worker suite passes 147 checks. App TypeScript, ESLint, Vite build, and
Prettier pass. Browser QA on a local production build confirmed the Thai

## F5d-33 rollout review, F5d-34 source-only remediation

F5d-33 independently re-verified F5d-32's implementation against actual Firestore/emulator behavior instead of trusting the prior report, and found the allocator was source-correct but not live-safe: the Worker's Firestore commit was malformed, the checked-in update Rule would deny every ordinary update to a pre-existing (pre-F5d-32) Service Job, and the Worker's CORS configuration would block the browser preflight for every authenticated call. F5d-34 fixed all three in source only, plus two related hardening items, with no deployment.

`worker/src/firestoreClient.ts`'s `commitServiceJobCreation` built every `:commit` write's `update.name` as a full HTTP URL rather than Firestore's required bare resource name (`projects/{project}/databases/(default)/documents/{collection}/{id}`) — confirmed against a local Firestore emulator to return `400` before Rules or IAM were ever reached. The resource name is now derived independently of the fetch base URL (which differs between the emulator and real Firestore). `worker/test/serviceJobAllocatorCommit.test.mts` is new: it drives `allocateServiceJob` through the real `createFirestoreClient()` implementation, stubbing only `fetch`, and asserts every write's `update.name` in the captured commit body is a bare resource path — closing the gap where every existing allocator test only exercised a hand-rolled fake `ServiceJobCreationDataAccess` and could not have caught this.

`firestore.rules`'s `serviceJobs` update rule paired its diff/`affectedKeys()` immutability guard (missing-field-safe) with redundant direct equality checks on `createdAt`/both public-tracking hash fields, which throw `Property ... is undefined on object` the instant a legacy document lacks one of those fields — denying ordinary updates to any Service Job created before F5d-32. Removed the three throwing lines; the diff-based guard alone already proves the same property. The pre-existing Firestore Rules emulator test for this exact scenario (`existing authorized ServiceJob updates preserve privileged fields and deny delete`) now passes; the suite is 10/10, up from the 9/10 F5d-33 found.

`worker/src/cors.ts`'s `Access-Control-Allow-Headers` allowed only `Content-Type`/`X-File-Name`; `Authorization` (every authenticated route) and `Idempotency-Key` (`POST /service-jobs`) are neither CORS-safelisted, so a real browser would block its own preflight before the Worker ever saw the request. Both are now allowed. `worker/test/cors.test.mts` is new — no preflight test existed before.

Two related fixes: the intake timeline's `time` field used `toLocaleTimeString` with no explicit zone (resolves to the Workers runtime default, UTC, not Bangkok — now `timeZone: 'Asia/Bangkok'`, matching the date field's existing math), and the ~32 KB-per-photo intake limit (unrealistic for a compressed camera photo) is now 300 KB/photo with a 700 KB aggregate cap and `MAX_INTAKE_BYTES` raised to 900 KB — sized against Firestore's 1 MiB per-document ceiling, since intake photos are embedded as base64 data URLs directly on the ServiceJob document. This does not make raw multi-MB camera photos work; that would need client-side compression or moving photos to the attachments/R2 pipeline, out of this fix's scope and flagged as a deferred limitation rather than silently left unaddressed.

Also: `ServiceReportsSection` now renders an explicit unavailable state under a non-Mock backend (Service Report Rules still don't exist, so the durable repository provider already rejected every write; the UI previously still offered a "Create Report" action that was guaranteed to fail). `src/config/filesBackend.ts` now fails closed the same way `backend.ts` already does, specifically for production with a durable (Firestore) business backend and a missing/mock files backend — previously a silent downgrade (durable jobs, non-durable attachments) with no error; `App.tsx` combines both configuration axes into the existing gate via a new `combineBackendConfigurations` helper.

Full validation: app TypeScript build, ESLint, Vite production build pass; serialized application suite 125/126 (the 126th, Firestore Rules, needs the emulator and runs separately); Firestore Rules emulator suite 10/10; Worker TypeScript typecheck and full Worker test suite pass. Prettier's pre-existing 8-markdown-file failures are unchanged.
